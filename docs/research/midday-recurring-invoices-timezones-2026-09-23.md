# Midday recurring invoices and time zones

## Question

How does Midday use `date-fns` and `@date-fns/tz` for recurring invoices, and which parts should Accly Books use?

## Answer

**Keep `@date-fns/tz`; add direct `date-fns` use only when implementing a recurrence rule that needs calendar arithmetic.** Midday's server uses the two packages together to calculate an invoice's next scheduled instant in its stored IANA zone. That is useful precedent for a future Books scheduler. It does not justify replacing Books' current `YYYY-MM-DD` accounting dates, UTC-pinned date-only display, organization-local “today,” or `Intl` instant formatting ([Midday calculator](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/utils/invoice-recurring.ts#L114-L244); [Books schema](../../packages/db/src/schema/documents.ts); [Books date conversion](../../packages/api/src/lib/business-date.ts); [Books organization datetime](../../apps/web/src/lib/org-datetime.ts)).

This note extends the [earlier offset investigation](./midday-timezones-2026-09-22.md). That investigation answered whether the _current_ Books code should migrate. A planned recurring-invoice feature creates a new calendar-arithmetic use case; it does not change the answer for existing call sites ([earlier conclusion](./midday-timezones-2026-09-22.md#answer); [Books current use](../../apps/web/src/lib/org-datetime.ts)).

## Evidence

### Midday's authoritative recurrence path

At Midday `main` commit [`51587319f26a0ffaa9dfccab1920373cb65689b7`](https://github.com/midday-ai/midday/tree/51587319f26a0ffaa9dfccab1920373cb65689b7), a recurring series stores its frequency parameters, IANA timezone, end condition, count, and `nextScheduledAt` timestamp. Its input schema supports weekly, biweekly, several monthly rules, quarterly, semiannual, annual, and custom day intervals ([table](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/schema.ts#L776-L813); [input schema](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/api/src/schemas/invoice-recurring.ts#L10-L105)).

The server calculator applies `date-fns` calendar functions to a `@date-fns/tz` date in the series zone, then returns a plain `Date` instant for storage. For a monthly date such as the 31st, it clamps to the target month's last day while retaining the requested day for later months. “Last day of month” is a separate recurrence rule ([calculator](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/utils/invoice-recurring.ts#L114-L244)). This use matches date-fns v4's explicit `in: tz(zone)` calculation context ([official time-zone guide](https://github.com/date-fns/date-fns/blob/main/pkgs/core/docs/timeZones.md#using-in-option)).

An hourly UTC worker selects active series whose `nextScheduledAt` is due. It creates the invoice and advances the series in one database transaction. A unique `(invoiceRecurringId, recurringSequence)` index backs duplicate prevention. When a run is late, the calculator moves to a future slot instead of generating every missed interval ([scheduler](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/worker/src/schedulers/invoices.config.ts#L1-L19); [due query](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/queries/invoice-recurring.ts#L447-L500); [transaction](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/worker/src/processors/invoices/generate-recurring.ts#L348-L396); [unique index](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/schema.ts#L1012-L1015); [advance](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/queries/invoice-recurring.ts#L517-L594)).

### Midday choices that do not transfer unchanged

- **Invoice issue day:** The worker takes the _UTC_ calendar day of `nextScheduledAt` for `issueDate` and adds the due-date offset from that anchor ([worker](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/worker/src/processors/invoices/generate-recurring.ts#L331-L343)). **Inference:** a run scheduled for 00:30 on 1 January in Asia/Kolkata has a 31 December UTC date; copying this path would put the wrong organization-local `documentDate` on a Books invoice. Books explicitly defines `documentDate` in the organization zone and derives its financial year from that date ([Books contract](../specs/accounting-core.md#architecture-calls); [Books schema](../../packages/db/src/schema/documents.ts); [Books numbering](../../packages/api/src/core/numbering.ts)).
- **Client preview:** Midday calls its client recurrence preview simplified and without timezone support. Books should use its eventual authoritative server rule for a preview, or label a cheaper preview as approximate ([Midday client utility](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/invoice/src/utils/recurring.ts#L286-L305); [Midday server calculator](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/utils/invoice-recurring.ts#L114-L244)).
- **Timezone owner:** Midday's form sends a user's saved or browser-detected timezone. Books stores an organization timezone and uses it for accounting dates. **Inference:** Books should make the organization's zone explicit in a recurrence rule and decide what a later settings change does to existing rules ([Midday form](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/dashboard/src/components/invoice/form.tsx#L336-L338); [Books settings](../../packages/db/src/schema/organization-settings.ts); [Books time contract](../specs/accounting-core.md#architecture-calls)).
- **General date utilities:** Midday uses UTC `TZDate` values for date-only UI and ordinary device-local `date-fns` operations for dashboard presets. Books already handles date-only display and organization-based presets without those conversions; a broad replacement would add a second date convention ([Midday date utility](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/dashboard/src/utils/date.ts#L1-L22); [Midday presets](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/dashboard/src/utils/date-presets.ts#L1-L105); [Books presets](../../apps/web/src/lib/date-presets.ts); [Books display](../../packages/api/src/lib/business-date.ts)).

### Current Books fit

Books stores `documentDate` and `dueDate` as PostgreSQL dates returned as strings, and `postedAt` as an instant. The API derives default document dates and overdue status from the organization zone. The web app directly depends on `@date-fns/tz` only for `tzOffset` in wall-clock conversion; `date-fns` is present through React DayPicker rather than as a declared API dependency ([schema](../../packages/db/src/schema/documents.ts); [invoice paths](../../packages/api/src/routers/invoice.ts); [web conversion](../../apps/web/src/lib/org-datetime.ts); [web dependencies](../../apps/web/package.json); [API dependencies](../../packages/api/package.json); [lock entries](../../bun.lock)).

## What this proves / does not prove

Midday demonstrates a working design that separates a zoned recurrence calculation from a stored due instant and gives each generated invoice a durable sequence. Its source establishes its month-end clamp and missed-run skip behavior ([calculator](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/utils/invoice-recurring.ts#L114-L244); [schema](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/schema.ts#L1012-L1015); [advance](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/queries/invoice-recurring.ts#L517-L594)).

I found no stated policy or DST-zone server test for a nonexistent or repeated local run time in the inspected calculator and server tests. This is a search-limited absence, not proof of incorrect runtime behavior. Its after-commit delivery queue can also fail after a draft is saved; this is a separate delivery contract, not a date-library property ([calculator](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/utils/invoice-recurring.ts#L114-L244); [server tests](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/test/invoice-recurring.test.ts); [delivery enqueue](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/worker/src/processors/invoices/generate-recurring.ts#L416-L488)).

## What this means for us

1. Keep the current narrow `@date-fns/tz` dependency and existing Books date model. Do not move calendar-only accounting fields to timestamps ([Books schema](../../packages/db/src/schema/documents.ts); [Books conversion](../../apps/web/src/lib/org-datetime.ts)).
2. When recurring invoices are specified, decide the anchor day, short-month rule, scheduled local time, DST gap/fold rule, missed-run policy, and effect of changing the organization zone. These are product contracts that Midday's calculator and worker make observable; the package cannot choose them for Books ([Midday calculator](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/utils/invoice-recurring.ts#L114-L244); [Midday advance](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/queries/invoice-recurring.ts#L517-L594); [Books contract](../specs/accounting-core.md#architecture-calls)).
3. Add `date-fns` and `@date-fns/tz` as direct dependencies of the scheduler's owning package if that rule needs named-zone calendar arithmetic. Derive invoice `documentDate` from the organization-local scheduled day. Store the next due instant separately. Back generated occurrences with a tenant-scoped unique key and create each invoice plus schedule advance atomically. This is a recommendation inferred from Midday's execution path and Books' tenant and accounting invariants ([date-fns guide](https://github.com/date-fns/date-fns/blob/main/pkgs/core/docs/timeZones.md#using-in-option); [Midday transaction](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/worker/src/processors/invoices/generate-recurring.ts#L348-L396); [Books schema](../../packages/db/src/schema/documents.ts); [Books org rule](../../AGENTS.md)).

## Next falsification

Before a recurrence spec, prototype one monthly rule from a 31 January anchor in an organization zone, crossing a short month and a DST transition. Compare the generated calendar date and stored instant under UTC, Los Angeles, and Tokyo host zones. Verify retry and late-worker behavior with a unique occurrence key. If the rule needs only date-only arithmetic and a daily scan, test whether the current business-date string model suffices before adding server-side date libraries ([Books date model](../../packages/api/src/lib/business-date.ts); [Midday calculator](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/packages/db/src/utils/invoice-recurring.ts#L114-L244); [Midday worker](https://github.com/midday-ai/midday/blob/51587319f26a0ffaa9dfccab1920373cb65689b7/apps/worker/src/processors/invoices/generate-recurring.ts#L348-L396)).
