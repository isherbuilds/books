### `PR4-P2-MUTABLE-MASTER-TX` and `PR4-P3-RACE-HELPER`

Receipt resolves active Party and income Account after entering its transaction (`packages/api/src/routers/receipt.ts:92-116`). Payment does the same for Party, expense Account, and dated TDS Section (`packages/api/src/routers/payment.ts:60-103`). Account and Payment Method reads are likewise held in the posting transaction (`packages/api/src/lib/accounts.ts:38-69`; `packages/api/src/core/documents.ts:184-215`). All predicates retain `orgId`.

The exact real-PostgreSQL proof comprised four races:

1. Receipt Account archive blocked, then posting refused `INCOME_ACCOUNT_INVALID`.
2. Payment Account archive blocked, then posting refused `EXPENSE_ACCOUNT_INVALID`.
3. Payment TDS validity update blocked, then posting refused `TDS_SECTION_INVALID`.
4. Receipt Party archive blocked, then posting refused `PARTY_INVALID`.

After all four, the SQL document count was unchanged. This scope proves the blocking/refusal/rollback contract for those races; it is not a general serializability or load claim.

The corrected `raceLockChange` helper uses the exact holder PID, paced probes, a deadline, explicit outcomes, and release/await cleanup (`tests/integration/lock.test.ts`). The old helper's confirmed weaknesses were 5,000 unpaced queries, an unscoped waiter match, ineffective exhaustion diagnostics, and incomplete failure cleanup—not a demonstrated inability to see transaction waits.

A follow-up PostgreSQL 18.6 probe held the settings row `FOR SHARE`, started a competing update, and ran the **original** tuple-lock predicate. It returned `blocked: true`. The waiting backend had:

| locktype      | mode          | granted | wait event           | blocker count |
| ------------- | ------------- | ------- | -------------------- | ------------- |
| transactionid | ShareLock     | false   | Lock / transactionid | 1             |
| transactionid | ExclusiveLock | true    | Lock / transactionid | 1             |
| tuple         | ExclusiveLock | true    | Lock / transactionid | 1             |

Both probe transactions rolled back. This directly rejects the claimed detection premise. PostgreSQL documents these transaction-ID waits and recommends `pg_blocking_pids()` for blocker relationships ([`pg_locks`](https://www.postgresql.org/docs/18/view-pg-locks.html), [`pg_blocking_pids`](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-INFO-SESSION-TABLE)).

### `PR4-PERF-EXCEPTION-INDEX`

The schema already has `(org_id, user_id, expires_at)` (`packages/db/src/schema/period-locks.ts:53-58`; generated SQL at `packages/db/src/migrations/0000_violet_newton_destine.sql:470-474`). PostgreSQL 18 may use skip scan on multicolumn B-trees ([multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html)); the observed plans used the existing index rather than scanning the whole heap.

| Isolated fixture             | Existing index            | Candidate partial index   |
| ---------------------------- | ------------------------- | ------------------------- |
| 2,000 rows total; 6 active   | 0.038 ms, 5 local buffers | 0.011 ms, 2 local buffers |
| 200,000 rows total; 7 active | 0.498 ms, 111 pages       | 0.041 ms, 9 pages         |

These are synthetic, temporary-table, single-run access-path measurements on PostgreSQL 18.6: half of each fixture belonged to the target organization, half to another, with 100 users. They exclude joined user reads, complete `lock.get`, network cost, repeated runs, and production distributions. PostgreSQL cautions that `EXPLAIN` timing and cost are environment-dependent ([`EXPLAIN`](https://www.postgresql.org/docs/18/using-explain.html)). The candidate can improve this isolated path, but no reported latency or buffer problem justifies extra schema weight; it was not added.

The final reconciliation also measured the complete exception-list SELECT, including both user joins, with the existing index on temporary tables: 200,000 exceptions across two organizations, 100 users, and 7 active rows for the target organization. Five `EXPLAIN (ANALYZE, BUFFERS)` runs took 1.248 ms initially and 0.093–0.101 ms warm, returning 7 rows; warm plans used 162 local buffer hits and the existing index. The transaction rolled back all fixtures. This remains synthetic SQL evidence, not endpoint latency or production distribution evidence; no additional index was justified or added.
